## GitHub Actions workflow monitoring failure -- separate from the job

GitHub Actions run `35474831164`'s "Locate the triggered run" step failed
with:

```text
Error: azure-cli auth: not configured. Config: host=https://dbc-1750318a-76a9.cloud.databricks.com, ...
```

That host (`dbc-1750318a-76a9...`) and the account/workspace identifiers
in the full error are Personal DEV's, not Azure PROD's, even though the
step explicitly set `DATABRICKS_HOST` to the Azure PROD host. Root cause:
the step's working directory (`labs/lab_08_cicd_travelops`, inherited from
the job's `defaults.run.working-directory`) contains `databricks.yml`,
whose default bundle target is `personal_dev`. The Databricks CLI performs
bundle-context auto-detection for *any* command run inside a directory
containing a bundle config file -- including plain, non-`bundle` commands
like `databricks jobs list-runs` -- and this silently overrode the
explicit `DATABRICKS_HOST` environment variable with the bundle's default
target's host. The two earlier steps in the same job
(`databricks bundle plan -t azure_prod` and
`databricks bundle run ... -t azure_prod`) were unaffected because they
explicitly name their bundle target, which overrides the default.

**This is a defect in the monitoring workflow only.** The Databricks job
itself was triggered successfully (confirmed by the "Trigger the job"
step's own log, which printed the correct Azure PROD run URL) and ran to
completion independently of GitHub Actions' inability to then locate and
poll it. A minimal fix (running the standalone CLI steps from a working
directory with no `databricks.yml` in it, e.g. `${{ runner.temp }}`) has
been proposed but not yet implemented in this evidence-only change.
